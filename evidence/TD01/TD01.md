# TD01 : conteneur web nommé

## Faits relevés
- Référence de l'image : nginxinc/nginx-unprivileged:1.29-alpine@sha256:8059701048a6cc7d64e8ab2812a44be70161bfa9ecfc01d69e95b8ff2a648705
- ID du conteneur : fef506bae907f1ebf687c6db4c5bb2e981afa8d3f9adf60e5e67741b52168901
- État : running (Up 10 minutes au moment de la mesure)
- Processus (docker top) : nginx master process (PID 849) et 8 processus worker (PID 896 à 903)
- Liaison de port (docker port) : 8080/tcp -> 127.0.0.1:8080
- Requête HTTP : HTTP/1.1 200 OK, page « Welcome to nginx! », 896 octets, Server nginx/1.29.8

## Explications
- Processus en cours : `docker top td01-web` le prouve, car il liste les vrais processus nginx qui tournent dans le conteneur. Le champ `state=running` de `docker inspect` est seulement l'état enregistré par Docker, `docker top` montre les processus eux-mêmes.
- Liaison avec l'hôte : `docker port td01-web` le prouve, car il affiche l'adresse de l'hôte et les deux ports (`8080/tcp -> 127.0.0.1:8080`). `docker ps` donne la même information dans la colonne PORTS.
- Succès HTTP : `curl -i http://127.0.0.1:8080/` le prouve, car il obtient une vraie réponse `200 OK` avec la page. Un conteneur « Up » et un port publié ne garantissent pas que nginx répond. Les logs le confirment (ligne `GET / HTTP/1.1" 200`), mais la preuve directe est la réponse de curl.

## Adresse de liaison
L'adresse est 127.0.0.1, donc une adresse de bouclage : seule cette machine peut atteindre le service. Preuve : la sortie de `docker port` et la colonne PORTS de `docker ps`. Une liaison générique afficherait 0.0.0.0 ou [::], ce qui n'est pas le cas ici.

## Étape 4 : arrêt, démarrage, suppression, recréation

Les prédictions sont dans `step4-predictions.txt`, écrites avant les commandes.

| Étape | Prédiction | Observé |
|---|---|---|
| `docker stop` | même ID, Exited, curl échoue, image présente | même ID, `Exited (0)`, `curl: (7)`, image présente |
| `docker start` | même ID, Up, curl 200 | même ID (`meme ID`), running, 200 OK |
| `docker rm` | conteneur absent, curl échoue, image présente | liste vide, `curl: (7)`, même ID d'image `sha256:8059...` |
| `./scripts/td01-run.sh` | nouvel ID, Up, curl 200 | ID `5c2474294c3c...`, running, 200 OK |

## Ce que prouvent ces résultats
- Arrêter puis redémarrer conserve le même conteneur (même ID) : rien n'est détruit.
- Supprimer détruit le conteneur (et son système de fichiers). L'image reste, donc le script recrée un conteneur neuf, avec un nouvel ID, sans nouveau téléchargement.
- Une requête échouée (`curl_exit=7`) prouve qu'un conteneur arrêté ou supprimé ne sert plus le web, même si l'image est là.
